## 13.2 数据协议规范

### 13.2.1 DTO 定义与变更流程

DTO（Data Transfer Object）是前后端通信的**唯一契约**，任何字段变更必须遵循以下流程：

```
提出变更 → 评审影响范围 → 更新 DTO 定义 → 同步三端 → 更新文档 → 发布通知
```

**具体步骤**：

| 步骤 | 执行者 | 输出物 | 检查点 |
|------|--------|--------|--------|
| 1. 提出变更 | 任意开发者 | DTO 变更提案（PR 描述或 Issue） | 说明变更原因和影响范围 |
| 2. 评审影响 | 模块负责人 + 前端 Leader | 评审结论 | 确认是否需要版本号变更 |
| 3. 更新定义 | 开发者 | Rust DTO struct + TS 类型 + 文档 | 三端定义必须一致 |
| 4. 同步三端 | 开发者 | Rust/TS/Python 代码 | 用 `serde` 自动映射验证 |
| 5. 更新文档 | 开发者 | 02-MVVM分层详解.md 对应章节 | DTO 示例与代码一致 |
| 6. 发布通知 | 模块负责人 | 企业微信/Slack 通知 | 所有消费者已知晓 |

**DTO 变更类型与处理方式**：

```typescript
// ✅ 安全变更（不需要版本号）
// 1. 新增可选字段（Rust Option<T>，TS ?:）
// 2. 字段重命名（需同步三端，一次性提交）

// ⚠️ 危险变更（需要版本号或迁移）
// 1. 删除字段 → 先标记 deprecated，保留 2 个版本后再删
// 2. 字段语义变更 → 新增字段，旧字段标记 deprecated
// 3. 类型变更 → 需要 DbVersion bump + 迁移脚本
```

**DTO 定义模板**（新增实体时必须复制此模板）：

```rust
// domain/dtos/article_dto.rs

/// 文章 DTO — 与 TypeScript domain/Article.ts 一一对应
///
/// 变更记录：
/// - v1 (2026-03-15): 初始版本
/// - v2 (2026-06-20): 新增 `word_count` 字段（可选，向后兼容）
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]  // ← 关键：自动转换 snake_case ↔ camelCase
pub struct ArticleDTO {
    pub id: String,
    pub project_id: String,
    pub title: String,
    pub content: String,
    pub version: u64,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub word_count: Option<u32>,  // ← 新增可选字段模板
    pub created_at: String,        // ISO 8601
    pub updated_at: String,        // ISO 8601
}

// ❌ 禁止：手动写 camelCase 字段名（容易不一致）
// #[serde(rename = "projectId")]
// pub project_id: String,
```

```typescript
// domain/Article.ts

/**
 * 文章 DTO — 与 Rust domain/dtos/article_dto.rs 一一对应
 *
 * @see 02-MVVM分层详解.md §2.3 数据映射规则
 * @changes
 * - v1 (2026-03-15): 初始版本
 * - v2 (2026-06-20): 新增 word_count 字段
 */
export interface ArticleDTO {
  id: string;
  projectId: string;  // ← 自动从 Rust snake_case 映射
  title: string;
  content: string;
  version: number;
  wordCount?: number;  // ← 可选字段，旧版本后端不会发送此字段
  createdAt: string;   // ISO 8601
  updatedAt: string;   // ISO 8601
}
```

### 13.2.2 字段命名与类型映射规范

| 规则 | Rust | TypeScript | Python | 示例 |
|------|------|------------|--------|------|
| 命名单数实体 | `snake_case` | `camelCase`（自动） | `snake_case` | `project_id` |
| 命名集合字段 | `snake_case` + `s` 后缀 | `camelCase` + `s` 后缀 | `snake_case` + `s` 后缀 | `article_ids: Vec<String>` |
| 时间字段 | `String` (ISO 8601) | `string` (ISO 8601) | `str` (ISO 8601) | `created_at: String` |
| 可选字段 | `Option<T>` | `T \| undefined` | `Optional[T]` | `summary: Option<String>` |
| 枚举字段 | `#[derive(Serialize)]` + `snake_case` | `as const` + 类型联合 | `StrEnum` | `Status::Draft` → `"draft"` |
| 大数字 | `u64` / `i64` | `string`（避免精度丢失） | `str` | `version: u64` → `"123"` |

**⚠️ 关键：`u64`/`i64` 在 TypeScript 中必须用 `string` 传输**

```rust
// Rust — 正确
#[derive(Serialize)]
pub struct ArticleDTO {
    pub id: String,        // ✅ String，不是 u64
    pub version: u64,      // ✅ 但 version 是计数器，值在 Number.MAX_SAFE_INTEGER 内
    pub file_size: i64,    // ❌ 危险！应改为 String
}

// 修正
#[derive(Serialize)]
pub struct ArticleDTO {
    pub id: String,
    pub version: u64,         // ✅ 假设 version < 2^53
    pub file_size: String,    // ✅ i64 → String
}
```

### 13.2.3 枚举值管理规范

枚举值是前后端协议的**高风险区域**——Rust 重命名枚举变体但 TS 没更新，会导致运行时错误。

**统一管理方案**：

```
domain/enums/           ← 所有枚举定义集中存放
├── article_status.rs   ← Rust 定义
├── article_status.ts   ← TS 类型（手动同步，或代码生成）
└── ENUM_REGISTRY.md    ← 枚举注册表（人工维护，PR 必查）
```

**枚举注册表模板**（`domain/enums/ENUM_REGISTRY.md`）：

```markdown

| 枚举名 | Rust 位置 | TS 位置 | Python 位置 | 最后同步日期 | 负责人 |
|--------|----------|---------|------------|-------------|--------|
| ArticleStatus | domain/enums/article_status.rs | domain/ArticleStatus.ts | agent/skills/common/types.py | 2026-06-14 | @张三 |
| Permission | domain/auth/permission.rs | domain/Permission.ts | — | 2026-06-10 | @李四 |

## ArticleStatus

| 变体 | Rust | TS | Python | 说明 |
|------|------|-----|--------|------|
```

### 13.2.4 API 接口命名规范

所有 Tauri IPC 命令（`invoke` 调用）必须遵循统一命名：

```
{module}:{entity}:{action}
```

| 模块 | 前缀 | 示例 |
|------|------|------|
| 文章 | `article:` | `article:save`, `article:delete`, `article:list` |
| 项目 | `project:` | `project:create`, `project:update` |
| 配置 | `config:` | `config:get`, `config:set` |
| Agent | `agent:` | `agent:execute`, `agent:cancel` |
| 离线 | `offline:` | `offline:queue:push`, `offline:queue:pop` |

**参数顺序规范**（Rust Command Handler）：

```rust
// ✅ 标准参数顺序
#[tauri::command]
async fn article_save(
    state: State<'_, AppState>,      // 1. 状态
    window: Window,                  // 2. 窗口（需要鉴权时）
    article: ArticleDTO,             // 3. 业务参数（按语义分组）
    auto_save: bool,                // 3. 业务参数
) -> Result<ArticleDTO, AppError> { ... }

// ❌ 错误：参数顺序混乱
async fn article_save(
    article: ArticleDTO,
    state: State<'_, AppState>,     // ← state 应该在第一个
    ...
)
```

## 13.3 事件协议规范

### 13.3.1 事件命名强制规范（执行细则）

04 §4.2 定义了事件命名格式 `{module}:{entity}:{action}[:{scope}]`，本节规定**执行细则**。

**新增事件的前置检查清单**（PR 模板中必须勾选）：

```
□ 事件名是否已存在于 04 §4.2.4 事件目录？
  → 若不存在，在 04 文档中登记（PR 必须包含文档更新）
□ 事件名是否符合 {module}:{entity}:{action} 格式？
  → module/entity 必须是小写单数
  → action 必须是过去式（created/updated/deleted）
□ 是否可能与其他模块的事件冲突？
  → 搜索整个代码库的 listen 调用，确认没有意外监听
□ Payload 是否包含 version 字段（实体变更事件）？
  → 用于乐观更新冲突检测（详见 08 §8.3）
□ 事件是否需要去重（04 §4.4）？
  → 高频事件（如 streaming chunk）必须加 eventId + timestamp
```

**事件命名反模式**（禁止）：

```typescript
// ❌ 反模式 1：action 不是过去式
emit('article:article:save');     // 应该是 article:article:saved
emit('project:list');             // 应该是 project:project:listed（但列表事件通常用 fetch 而非事件）

// ❌ 反模式 2：module 和 entity 冗余但含义不同
emit('article:project:updated');  // 含义模糊：是文章的项目的更新？还是项目的更新？

// ❌ 反模式 3：scope 使用动态值
emit(`article:article:updated:${articleId}`);  // ← 会导致监听者需要动态构造事件名
                                              // 应该用 payload 传递 articleId
```

**正确做法**：

```typescript
// ✅ 标准事件发射
emit('article:article:updated', {
  articleId: article.id,
  version: article.version,
  updatedFields: ['title', 'content'],  // 可选：告知前端哪些字段变了
});

// ✅ 标准事件监听（在 ViewModel 层）
listen<ArticleUpdatedPayload>('article:article:updated', (event) => {
  const payload = event.payload;
  // 更新对应 article 的 RTK state
  dispatch(articleSlice.actions.articleUpdated(payload));
});
```

### 13.3.2 Payload 结构约定

所有事件 payload 必须遵循标准结构：

```typescript
// 标准 Payload 接口（必须遵守）
interface StandardEventPayload<T = unknown> {
  // 身份字段
  entityId: string;       // 变更的实体 ID
  version?: number;       // 实体版本号（实体变更事件必须）
  triggeredBy?: string;   // 触发者（window label 或 'system' 或 'agent'）

  // 数据字段
  data: T;                // 变更后的完整实体或变更摘要

  // 去重字段（高频事件必须）
  eventId?: string;       // UUID v4，用于去重（04 §4.4）
  timestamp?: number;     // Unix ms，用于去重
}

// 示例：文章更新事件
interface ArticleUpdatedPayload extends StandardEventPayload<Partial<ArticleDTO>> {
  entityId: string;
  version: number;
  triggeredBy: string;
  data: {
    id: string;
    title?: string;       // 仅包含变更的字段（轻量化）
    content?: string;
    updatedAt: string;
  };
  eventId: string;        // ← 去重必需
  timestamp: number;      // ← 去重必需
}
```

### 13.3.3 事件生命周期管理

事件与代码一样需要版本管理：

```
新增 → 使用 → 标记弃用 → 迁移消费者 → 删除
```

| 阶段 | 操作 | 要求 |
|------|------|------|
| 新增 | 在 04 §4.2.4 事件目录登记 | PR 必须包含文档更新 |
| 使用 | 正常监听 | 无 |
| 弃用 | 在事件名后加 `@deprecated` 注释 + 文档标注 | 保留 2 个版本（约 1 个月） |
| 删除 | 确认所有消费者已迁移 | 删除事件目录中的条目 |

**弃用标记模板**：

```typescript
// ⚠️ @deprecated 于 v1.3.0 — 使用 article:article:saved 替代
// 计划删除于 v1.5.0
listen('article:article:created', ...);
```

```markdown
<!-- 04-MVVM分层详解.md 事件目录 -->

| 事件名 | 含义 | 状态 |
|--------|------|------|
| `article:article:created` | 文章创建 | ✅ 活跃 |
| `article:article:saved` | 文章保存（取代 created）| ✅ 活跃 |
| `article:article:published` | 文章发布 | ⚠️ @deprecated v1.3.0，删除于 v1.5.0 |
```

### 13.4.2 跨模块协作流程

MirageInk 采用模块化单体架构（01 §1.4），模块间边界必须严格遵守：

```
module/
├── article/        ← 文章模块（Bounded Context）
│   ├── domain/     ← 领域模型（不依赖其他模块）
│   ├── repository/ ← 数据访问（只访问 article 相关表）
│   ├── usecase/    ← 业务逻辑（可调用其他模块的 Repository 只读）
│   └── commands/   ← IPC 命令（只暴露 article:* 命令）
├── project/        ← 项目模块
└── shared/         ← 共享内核（所有模块可依赖，但不能依赖具体模块）
    ├── domain/     ← 共享类型（AppError, Session, Permission）
    ├── events/     ← 事件定义
    └── utils/      ← 工具函数
```

**依赖规则**（强制）：

```
✅ 允许：article 模块 → shared 模块
✅ 允许：article 模块 → project 模块（文章依赖项目）
❌ 禁止：shared 模块 → article 模块（共享内核不能依赖具体模块）
❌ 禁止：article 模块 ↔ project 模块 双向依赖（循环依赖）
```

**循环依赖解决方案**：

```
问题：article 需要 project 的信息，project 也需要 article 的计数

解决方案 1：提取到 shared
  → 将共享概念提取为 shared/domain/article_summary.rs

解决方案 2：事件驱动
  → project 模块监听 article:article:created 事件，更新自己的计数
  → 不直接调用 article Repository

解决方案 3：依赖反转
  → 定义 trait ArticleRepositoryReadOnly in shared
  → article 模块实现，project 模块只依赖 trait
```

## 13.9 常见问题（FAQ）

**Q1：我只是改一个 CSS 样式，也需要遵守这些规范吗？**

A：不需要。本规范主要适用于涉及数据协议、事件、新增功能的代码变更。纯样式、文案、配置的变更可以简化流程。但 PR 模板中的 Checklist 仍然建议勾选（即使大部分不适用）。

**Q2：DTO 变更流程太重了，能不能跳过？**

A：如果是新增可选字段（`Option<T>` in Rust, `?:` in TS），可以简化流程（不需要版本号变更）。但如果是删除字段或语义变更，必须走完整流程。架构腐化往往从"小改动"开始。

**Q3：事件名冲突了怎么办？**

A：事件名全局唯一。如果两开发者同时新增了同名事件，CI 会自动检测并失败。解决方式：重命名其中一个事件，或在事件名中加入更具体的 module/entity 前缀。

**Q4：枚举值在三端不同步怎么办？**

A：这就是为什么要建立 ENUM_REGISTRY.md。每次变更枚举，必须更新注册表，并且 PR Review 者必须检查三端一致性。长期方案是用 `ts-rs` 自动生成 TS 类型。

**Q5：架构守护测试写起来很复杂，值得吗？**

A：对于 MVP 阶段，可以先不写。但当团队规模 > 3 人时，人工 Review 容易遗漏架构违规。架构守护测试是"一次编写，持续受益"。

## 13.11 架构决策记录（ADR）规范

### 13.11.1 什么是 ADR？

**架构决策记录（Architecture Decision Record）** 是记录**重要架构决策**的短文档。每个 ADR 描述一个已接受的架构决策，包括：

- **背景（Context）**：是什么问题驱动了这个决策？
- **决策（Decision）**：我们决定了什么？
- **后果（Consequences）**：这个决策让什么变容易了，又让什么变难了？

> **核心理念**：架构决策会过时，但**决策理由不会过时**。半年后新人问"为什么用 Tauri 不用 Electron？"，答案在 ADR 里，不在某人的记忆里。

### 13.11.2 什么时候需要写 ADR？

**必须写 ADR 的场景**（§13.1 提到的"重大变更"）：

| 场景 | 示例 | 是否必须 ADR |
|------|------|---------------|
| 技术栈选型 | "选择 Tauri v2 而非 Electron" | ✅ 必须 |
| 架构模式变更 | "从 Redux 迁移到 RTK" | ✅ 必须 |
| 数据模型重大变更 | "引入 version 字段做乐观更新" | ✅ 必须 |
| 安全架构决策 | "选择 SQLCipher 而非应用层加密" | ✅ 必须 |
| 第三方依赖引入 | "引入 LangChain 做 AI Agent 编排" | ✅ 必须（记录选型理由） |
| 跨模块通信机制 | "选择 Tauri Event 而非 WebSocket" | ✅ 必须 |
| Bug 修复 | "修复 version 溢出 bug" | ❌ 不需要 |
| 功能新增（无架构影响） | "新增文章标签功能" | ❌ 不需要 |
| 重构（不改变外部行为） | "提取 shared 模块" | ⚠️ 建议（如果涉及模块边界变更） |

**判断标准**：这个决策如果做错了，重构成本 > 2 人周？如果是 → 写 ADR。

### 13.11.3 ADR 文件规范

**目录结构**：

```
architecture/
├── 01-总体架构设计.md
├── ...
├── 13-团队协作与开发规范.md
└── adr/                              ← ADR 专用目录
    ├── ADR-001-tauri-v2-selection.md
    ├── ADR-002-sqlcipher-encryption.md
    ├── ADR-003-version-based-optimistic-update.md
    ├── ADR-004-langchain-agent-orchestration.md
    ├── ADR-005-field-level-lww-conflict-resolution.md
    └── ADR-TEMPLATE.md                ← 模板文件（复制即用的起点）
```

**编号规则**：

- 格式：`ADR-NNN-kebab-case-title.md`
- 编号：**全局递增**，不按模块分区（方便按时间排序）
- 标题：英文 kebab-case，简要描述决策主题
- 示例：`ADR-005-field-level-lww-conflict-resolution.md`

**ADR 状态机**：

```
Draft → InReview → Accepted → Deprecated → Superseded (by ADR-XXX)
  ↓
Cancelled（草稿阶段被否决）
```

| 状态 | 含义 | 可以修改？ | 可以合并到 main？ |
|------|------|------------|-------------------|
| `Draft` | 初稿，等待评审 | ✅ 是 | ❌ 否 |
| `InReview` | 正在评审中 | ⚠️ 仅修正拼写/格式 | ❌ 否 |
| `Accepted` | 已接受，执行中 | ❌ 否（只能追加 Addendum） | ✅ 是 |
| `Deprecated` | 已弃用，但历史可查 | ❌ 否 | ✅ 是 |
| `Superseded` | 被新 ADR 替代 | ❌ 否 | ✅ 是 |

### 13.11.5 ADR 评审流程

**谁参与评审？**

| 角色 | 必须参与的场景 |
|------|----------------|
| 架构师 | 所有 ADR |
| 模块负责人 | 涉及本模块的 ADR |
| 前端 Leader | 涉及前端架构的 ADR（状态管理、构建工具等） |
| 后端 Leader | 涉及后端架构的 ADR（数据库、API 设计等） |
| DevOps | 涉及 CI/CD、部署、监控的 ADR |
| 安全负责人 | 涉及安全架构的 ADR（加密、认证、授权等） |

**评审标准**（Reviewer 必须检查）：

```
□ Context 是否清晰？新人能否看懂为什么需要做这个决策？
□ Decision 是否明确？有没有模糊表述（"可能"、"也许"）？
□ Alternatives Considered 是否充分？是否认真考虑了至少 2 个替代方案？
□ Consequences 是否平衡？是否既写了优点也写了缺点？
□ 是否有隐藏的假设？假设是否合理？
□ 是否与现有架构文档冲突？如果冲突，哪个应该改？
□ Implementation Notes 是否可行？团队是否有能力执行？
```

**评审时间线**：

```
Day 0:   ADR 作者提交 Draft PR
Day 1-2: Reviewers 提供反馈
Day 3:   ADR 作者修订（Draft → InReview）
Day 4-5: Reviewers 二次评审
Day 5:   所有 Reviewer 批准 → 合并（Status: Accepted）
         有 Reviewer 否决 → 返回 Draft 或取消（Status: Cancelled）
```

**合并条件**（全部满足才能合并）：

1. ✅ 至少 2 名 Reviewer 批准（其中 1 名必须是架构师）
2. ✅ 所有 `Alternatives Considered` 的缺点描述具体（不能是"太复杂"这种模糊表述）
3. ✅ `Consequences/Negative` 至少 1 条（不允许只写优点不写缺点）
4. ✅ CI 检查通过（ADR 中的代码示例可运行，如果有）

### 13.11.6 ADR 生命周期管理

**修改已接受的 ADR**：

```
场景：实施过程中发现决策有遗漏
操作：在 ADR 末尾追加 Addendum，不修改原文

格式：

## Addendum (YYYY-MM-DD)

### 变更内容

[描述新发现或变更]

### 原因

[为什么需要变更？]

### 影响

[对原 Decision/Consequences 的影响]
```

**弃用 ADR**：

```
场景：决策已不再适用（但历史记录有价值）
操作：
1. 修改 Status 为 Deprecated
2. 在 Decision 章节末尾追加：
   > **⚠️ Deprecated (YYYY-MM-DD)**：[弃用原因]
3. 保留文件（不要删除，历史可查）
```

**替代 ADR**：

```
场景：新决策完全替代旧决策
操作：
1. 旧 ADR：修改 Status 为 `Superseded by ADR-XXX`
2. 旧 ADR：在 Decision 章节末尾追加：
   > **⚠️ Superseded by [ADR-XXX](./ADR-XXX-xxx.md) (YYYY-MM-DD)**：[替代原因]
3. 新 ADR：在 Context 章节引用旧 ADR：
   > **Note**：本决策替代 [ADR-NNN](./ADR-NNN-xxx.md)，因为 [原因]。
```

#### 示例 1：ADR-001 — 选择 Tauri v2 作为桌面应用框架

```markdown
# ADR-001: 选择 Tauri v2 作为桌面应用框架

## Status

Accepted

## Context

MirageInk 需要构建跨平台桌面应用（macOS + Windows + Linux）。
最初考虑 Electron，但遇到以下问题：
1. Electron 打包后体积 > 150MB（主要是 Chromium + Node.js）
2. 内存占用高（空窗口 ~150MB）
3. 安全边界不清晰（Chromium 渲染进程与 Node.js 主进程通信复杂）

团队有 Rust 经验，希望利用 Rust 的内存安全优势。

## Decision

选择 Tauri v2 作为桌面应用框架。

关键配置：
- 前端：React 18 + TypeScript
- 后端：Rust + Tauri v2 IPC
- 打包：默认打包含量 ~10MB（系统 WebView）

## Alternatives Considered

### Alternative 1: Electron

Electron 是成熟的桌面应用框架，生态丰富。

**优点**：
- 生态成熟，npm 包丰富
- 文档完善，社区大
- 热重载体验好（Vite）

**缺点**（未选择的原因）：
- 打包体积大（> 150MB），用户下载体验差 → **关键原因**
- 内存占用高，低配机器体验差
- 安全风险：Chromium CVE 需跟随更新，响应慢

### Alternative 2: Flutter Desktop

**优点**：
- 单一代码库（Dart）
- 性能接近原生

**缺点**：
- 团队无 Dart 经验，学习成本高 → **关键原因**
- WebView 集成不友好（MirageInk 需要富文本编辑器，基于 Web 技术更合适）

## Consequences

### Positive

- 打包体积降低 90%+（10MB vs 150MB）
- 内存占用降低（空窗口 ~40MB）
- Rust 后端提供内存安全保证
- 利用系统 WebView，外观与原生应用一致

### Negative

- 需要处理 macOS 签名公证（Apple Developer Program $99/年）
- Windows 侧需要额外处理 WebView2 运行时依赖
- 部分 npm 包不兼容 Tauri 的 CSP 策略（需要额外配置）

## References

- [01-总体架构设计.md §1.2](./01-总体架构设计.md#12-技术选型)
- [Tauri v2 Documentation](https://v2.tauri.app/)
```

#### 示例 2：ADR-005 — 字段级 LWW 冲突解决

```markdown
# ADR-005: 字段级 LWW 冲突解决

## Status

Accepted

## Context

MirageInk 支持离线编辑（09-离线缓存与冲突解决.md）。
最初设计是整行 LWW（Last-Write-Wins）：如果用户 A 修改了 title，用户 B 修改了 content，后同步的会覆盖整行。

这导致问题：用户 A 的 title 修改被用户 B 的 content 修改意外覆盖。

## Decision

将冲突解决粒度从**整行**细化到**字段级**：
- 每个字段独立比较时间戳
- 只有双方都修改了同一个字段，才需要 LWW 解决
- 不同字段的修改自动合并

详见 09 §9.5.2 `resolve_field_level_lww()` 实现。

## Alternatives Considered

### Alternative 1: 保留整行 LWW

**优点**：
- 实现简单
- 用户理解容易（"最后保存的赢"）

**缺点**：
- 意外覆盖风险高 → **关键原因**
- 需要用户手动解决冲突（体验差）

### Alternative 2: CRDT（如 Yjs）

**优点**：
- 无冲突合并
- 支持实时协作

**缺点**：
- 引入额外依赖（Yjs + y-py） → **关键原因**
- 学习成本高（团队无 CRDT 经验）
- MirageInk 是单用户离线场景，CRDT 过度设计

## Consequences

### Positive

- 意外覆盖减少 80%+（基于模拟测试）
- 用户无需手动解决冲突（大部分场景）
- 实现成本可控（~200 行 Rust 代码）

### Negative

- 冲突解决逻辑变复杂（需要按字段比较）
- 需要记录每个字段的修改时间戳（存储开销增加 ~10%）

## References

- [09-离线缓存与冲突解决.md §9.5](./09-离线缓存与冲突解决.md#95-冲突解决策略)
- [ADR-003: Version-based Optimistic Update](./ADR-003-version-based-optimistic-update.md)
```

### 13.11.8 ADR 工具推荐

**创建新 ADR**（自动化脚本）：

```bash
#!/bin/bash
# 脚本：scripts/new_adr.sh
# 用法：./scripts/new_adr.sh "选择 XXX 作为 YYY"

TITLE="$1"
KEBAB=$(echo "$TITLE" | tr '[:upper:]' '[:lower:]' | tr ' ' '-' | tr -d '.,!?()')
NEXT_NUM=$(ls architecture/adr/ADR-*.md 2>/dev/null | \
            sed 's/.*ADR-\([0-9]*\)-.*/\1/' | \
            sort -n | tail -1 | xargs -I{} expr {} + 1)
NEXT_NUM=$(printf "%03d" ${NEXT_NUM:-1})

FILENAME="architecture/adr/ADR-${NEXT_NUM}-${KEBAB}.md"

cp architecture/adr/ADR-TEMPLATE.md "$FILENAME"

# 替换模板中的 NNN 为实际编号
sed -i '' "s/ADR-NNN/ADR-${NEXT_NUM}/g" "$FILENAME"
sed -i '' "s/\[决策标题\]/$TITLE/g" "$FILENAME"

echo "Created: $FILENAME"
```

**列出所有 ADR**（快速查看状态）：

```bash
#!/bin/bash
# 脚本：scripts/list_adr.sh

echo "## ADR 列表"
echo ""

ls architecture/adr/ADR-*.md 2>/dev/null | while read f; do
  status=$(grep "^## Status" -A 1 "$f" | tail -1 | sed 's/^[^a-zA-Z]*//')
  title=$(head -1 "$f" | sed 's/# ADR-[0-9]*: //')
  echo "- [$status] $title → $f"
done
```
