# 01 — 总体架构设计

## 1.1 产品定位

MirageInk（智写时光）是一款基于 Tauri 2.x 的企业级多窗口桌面写作应用，核心能力包括：

- 多窗口文章创作与项目管理
- 内置 AI 写作助手（写作 / 分析 / 研究 / 润色）
- 本地优先，数据由 SQLite 管理，离线可用
- 安全的多窗口会话隔离

## 1.2 技术选型与理由

| 技术          | 选型理由                                              |
| ------------- | ----------------------------------------------------- |
| Tauri 2.x     | 原生桌面壳，体积小（~5MB），Rust 后端提供系统级能力    |
| React 18      | 成熟的前端生态，支持 Concurrent Rendering              |
| TypeScript    | 类型安全，与 Rust DTO 一一映射                         |
| RTK (Redux Toolkit) | 内置 Immer、createSlice、RTK Query，MVVM 的 ViewModel |
| Rust          | 零成本抽象、内存安全、SQLite 绑定（rusqlite）          |
| SQLite        | 嵌入式、事务支持、FTS5 全文搜索、本地离线              |
| Python 3.11+  | AI/LLM 生态（LangChain, OpenAI SDK, Ollama）           |
| FastAPI       | 异步 HTTP 框架 + 原生 SSE 支持                         |
| LangGraph     | Agent 编排引擎，支持多步骤推理与工具调用               |

## 1.3 四层技术栈与职责

```
┌──────────────────────────────────────────┐
│              表示层 (React + TS)           │
│    View + ViewModel + RTK Query           │
├──────────────────────────────────────────┤
│              应用层 (Rust)                │
│    Tauri Commands → UseCase → Domain      │
│    事务管理 · 权限控制 · 事件发射          │
├──────────────────────────────────────────┤
│              持久层 (SQLite)              │
│    业务数据 · 缓存 · 离线队列 · FTS5      │
├──────────────────────────────────────────┤
│              AI 服务层 (Python)            │
│    LangGraph Agent · SSE 流式 · Memory    │
└──────────────────────────────────────────┘
```

严格的单向依赖：表示层 → 应用层 → 持久层。AI 服务层通过 Bridge 回读应用层，不穿透持久层。

## 1.4 核心架构原则

### 原则 1：单一真理源

SQLite（Rust 独占）是唯一数据权威。前端不写 SQL、Python 不直连 DB，所有写操作必须经过 Rust UseCase。

### 原则 2：跨语言 MVVM

```
React (View + ViewModel)  ←→  Rust (Domain + Application + Infrastructure)
                                     ←→  Python (AI 微服务)
```

- React 通过 RTK Slice 实现 ViewModel，不直接操作数据
- Rust 通过 Event 将领域变更广播到所有窗口
- Python 仅作为推理引擎，通过 Bridge 回调获取 Rust 侧上下文

### 原则 3：窗口级状态隔离

每个 Tauri 窗口拥有独立的 React Root 和 RTK Store，窗口间通过 Tauri Event 同步领域数据变更，不共享 UI 状态。

### 原则 4：业务规则在 Rust

所有验证、权限判定、数据完整性约束在 Rust 侧实现。前端仅做 UI 级校验（表单非空等），不做业务校验。

### 原则 5：事件驱动同步

窗口间数据同步使用 Tauri Global Event（推送），不使用轮询。前端 listen → dispatch → UI 自动刷新。

## 1.6 关键设计决策记录

| 决策点                 | 选定方案            | 替代方案（已否决）     | 否决理由                     |
| ---------------------- | ------------------- | ---------------------- | ---------------------------- |
| 桌面框架               | Tauri 2.x           | Electron               | 体积大、内存高               |
| 状态管理               | RTK                 | Zustand / MobX         | RTK 生态更完善、中间件丰富   |
| 多窗口 Store            | 每窗口独立          | 全局共享 Store         | 多窗口 bug 根源              |
| 后端语言               | Rust                | Node.js                | 缺少 SQLite FTS5 原生绑定    |
| AI 语言                | Python 子进程       | Rust 原生 LLM 绑定     | AI 生态集中在 Python         |
| Python ↔ Rust 通信     | HTTP Bridge         | stdin/stdout 管道      | 需双向通信、SSE 流式支持     |
| 离线冲突               | Last-Write-Wins + 手动 | CRDT（Automerge）    | 复杂度高、桌面场景不需要     |

## 1.7 非功能需求

| 类别       | 指标                        |
| ---------- | --------------------------- |
| 冷启动时间 | < 2s（含 Python Agent 启动） |
| 窗口响应   | < 100ms（invoke 往返）       |
| 事件延迟   | < 50ms（emit → listen）     |
| 内存占用   | < 300MB（含 3 窗口 + Agent） |
| 安装包大小 | < 30MB                       |
| 离线可用   | 核心增删改查全部可用         |
| 数据安全   | SQLite 文件加密（SQLCipher） |
