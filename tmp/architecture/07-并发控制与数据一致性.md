# 07 — 并发控制与数据一致性

## 7.1 并发场景分析

MirageInk 的并发场景来自多个维度：

| 并发来源               | 说明                                 |
| ---------------------- | ------------------------------------ |
| 多窗口同时操作同一数据 | 用户在不同窗口编辑同一项目           |
| Rust 侧多线程          | Tauri Command 默认异步多线程          |
| Python Agent 回调      | Bridge 回调发生在独立线程             |
| 事件发射与处理          | 事件去重和清理在独立线程              |
| 看门狗检测              | 每 10s 的异步健康检查                 |

## 7.2 并发控制策略总览

```
┌─────────────────────────────────────────────────┐
│              并发控制分层                         │
│                                                 │
│  前端层：乐观更新 + 版本号比对 + 自动回滚          │
│    ↕ invoke                                      │
│  Rust 层：SQLite 事务 + 乐观锁 + Mutex/RwLock    │
│    ↕                                             │
│  SQLite：WAL 模式 + 行级锁 + 文件锁               │
└─────────────────────────────────────────────────┘
```

## 7.3 SQLite 并发模型

### 7.3.1 WAL (Write-Ahead Logging) 模式

```rust
// infrastructure/database.rs
pub fn configure_connection(conn: &Connection) {
    conn.execute_batch("
        -- WAL 模式：读写不互斥
        PRAGMA journal_mode = WAL;
        -- 外键约束
        PRAGMA foreign_keys = ON;
        -- 忙等待超时（5s），而非立即返回 SQLITE_BUSY
        PRAGMA busy_timeout = 5000;
        -- 同步模式：NORMAL 在 WAL 下安全且性能更好
        PRAGMA synchronous = NORMAL;
        -- WAL 自动检查点（页数达到阈值时）
        PRAGMA wal_autocheckpoint = 1000;
    ").expect("Failed to configure database");
}
```

**WAL 模式下的并发保证**：
- 多个读操作完全并发（不互相阻塞）
- 写操作串行化（SQLite 内部写锁）
- 读写不互斥（读可以看到写开始前的快照）
- 多个连接可以同时持有读锁

### 7.3.2 连接池配置

```rust
// infrastructure/database.rs
use r2d2::Pool;
use r2d2_sqlite::SqliteConnectionManager;

pub fn create_pool(db_path: &Path) -> Pool<SqliteConnectionManager> {
    let manager = SqliteConnectionManager::file(db_path);
    Pool::builder()
        .max_size(8)            // 最多 8 个连接
        .min_idle(Some(2))      // 保持 2 个空闲连接
        .connection_timeout(Duration::from_secs(10))
        .build(manager)
        .expect("Failed to create connection pool")
}
```

## 7.4 Rust 侧并发原语

### 7.4.1 共享状态保护

```rust
// app_state.rs
use std::sync::{Arc, RwLock, Mutex};

pub struct AppState {
    // 读写比高的数据用 RwLock（多读少写）
    pub config: RwLock<AppConfig>,
    pub session_manager: Arc<SessionManager>,  // 内部使用 RwLock

    // 写频率高的用 Mutex
    pub dedup_state: Mutex<HashSet<EventKey>>,

    // 线程安全的连接池
    pub db_pool: Pool<SqliteConnectionManager>,

    // 跨线程通信
    pub agent_status_tx: broadcast::Sender<AgentStatus>,
}
```

### 7.4.2 RwLock vs Mutex 选择指南

| 场景                         | 选择    | 理由                       |
| ---------------------------- | ------- | -------------------------- |
| 配置读取（多读少写）         | RwLock  | 读不互斥，高并发           |
| 会话管理（多读少写）         | RwLock  | 大量窗口同时读取自己的会话 |
| 事件去重 HashSet（读写相当） | Mutex   | 操作原子、持有时间极短     |
| 连接池                       | 内置安全 | r2d2 内部已处理            |

### 7.4.3 死锁预防规则

1. **锁获取顺序一致**：始终按 `session → config → db` 顺序获取
2. **锁持有时间短**：不在持有锁时进行 I/O 或网络操作
3. **避免嵌套锁**：不同锁类型不嵌套

```rust
// 正确 ✅：锁获取顺序固定
fn update_article(state: &AppState, ...) -> Result<(), AppError> {
    // 1. 先获取 session（RwLock read）
    let session = state.session_manager.resolve_from_window(label)?;

    // 2. 权限校验（不持有锁）
    state.auth.check_permission(&session, Permission::ArticleWrite, None)?;

    // 3. 从连接池获取连接（不持有应用锁）
    let conn = state.db_pool.get()?;

    // 4. 事务执行
    conn.execute("BEGIN IMMEDIATE", [])?;
    // ... SQL operations
    conn.execute("COMMIT", [])?;

    Ok(())
}
```

## 7.5 乐观锁

### 7.5.1 版本号方案

```rust
// domain/article.rs
pub struct Article {
    pub version: u32,  // 乐观锁版本号
    // ...
}
```

### 7.5.2 冲突检测

```rust
// application/article_usecase.rs
impl ArticleUseCase {
    pub fn update_with_optimistic_lock(
        &self,
        id: &str,
        content: &str,
        client_version: u32,     // 前端持有的版本号
    ) -> Result<Article, AppError> {
        let conn = self.pool.get()?;

        // 原子操作：仅当版本号匹配时才更新
        let new_version = client_version + 1;
        let affected = conn.execute(
            "UPDATE articles
             SET content = ?1, version = ?2, updated_at = datetime('now')
             WHERE id = ?3 AND version = ?4",
            params![content, new_version, id, client_version],
        )?;

        if affected == 0 {
            // 版本冲突：获取当前版本号返回给前端
            let current: Article = conn.query_row(
                "SELECT * FROM articles WHERE id = ?1",
                params![id],
                |row| Ok(Article::from_row(row)),
            )?;
            return Err(AppError::VersionConflict {
                current_version: current.version,
                client_version,
            });
        }

        // 读取更新后的实体
        self.find_by_id(id)
    }
}
```

### 7.5.3 前端冲突处理

```typescript
// 乐观更新的冲突处理
const saveArticle = createAsyncThunk(
  'articleEditor/save',
  async (article: ArticleDTO, { rejectWithValue }) => {
    try {
      return await invoke<ArticleDTO>('article:update', {
        id: article.id,
        content: article.content,
        clientVersion: article.version,
      });
    } catch (error) {
      if (isVersionConflictError(error)) {
        // 返回冲突信息
        return rejectWithValue({
          code: 'VERSION_CONFLICT',
          currentVersion: error.currentVersion,
          serverArticle: error.serverArticle,  // Rust 返回的最新版本
        });
      }
      throw error;
    }
  }
);

// Reducer 中处理冲突
builder.addCase(saveArticle.rejected, (state, action) => {
  if (action.payload?.code === 'VERSION_CONFLICT') {
    state.saveStatus = 'conflict';
    state.conflictInfo = {
      serverVersion: action.payload.currentVersion,
      serverArticle: action.payload.serverArticle,
    };
  } else {
    state.saveStatus = 'failed';
  }
});
```

## 7.6 事务隔离级别

### 7.6.1 事务模式对比

| 模式              | 行为                           | 使用场景               |
| ----------------- | ------------------------------ | ---------------------- |
| `BEGIN`           | 延迟锁，首次写时才获取         | 简单只读后可能写       |
| `BEGIN IMMEDIATE` | 立即获取预留写锁               | 确定会写的事务（推荐） |
| `BEGIN EXCLUSIVE` | 立即获取排他锁，阻塞所有读     | 关键数据迁移           |

### 7.6.2 推荐模式

```rust
pub fn save_article_with_relations(
    conn: &Connection,
    article: &Article,
    tags: &[Tag],
) -> Result<(), AppError> {
    // BEGIN IMMEDIATE：防止死锁，立即声明写意图
    conn.execute("BEGIN IMMEDIATE", [])?;

    let result = (|| {
        // 1. 更新文章
        conn.execute(
            "UPDATE articles SET content = ?1, version = ?2 WHERE id = ?3 AND version = ?4",
            params![article.content, article.version + 1, article.id, article.version],
        )?;

        // 2. 更新标签关联（多表操作需要事务）
        conn.execute("DELETE FROM article_tags WHERE article_id = ?1", params![article.id])?;
        for tag in tags {
            conn.execute(
                "INSERT OR REPLACE INTO article_tags (article_id, tag_id) VALUES (?1, ?2)",
                params![article.id, tag.id],
            )?;
        }

        Ok::<_, AppError>(())
    })();

    match result {
        Ok(_) => {
            conn.execute("COMMIT", [])?;
            Ok(())
        }
        Err(e) => {
            conn.execute("ROLLBACK", [])?;
            Err(e)
        }
    }
}
```

## 7.7 多窗口并发写入

### 7.7.1 场景

```
Window A: 编辑文章 #1 → 保存 (version=5)
Window B: 编辑文章 #1 → 保存 (version=5)  ← 冲突！
```

### 7.7.2 时序图

```
Window A              Rust/SQLite              Window B
  │                       │                       │
  │─ save(v=5) ──────────►│                       │
  │                       │ BEGIN IMMEDIATE        │
  │                       │ UPDATE WHERE v=5 ✓ (v→6)│
  │                       │ COMMIT                 │
  │◄─── success(v=6) ────│                       │
  │                       │                       │─ save(v=5) ──►
  │                       │                       │              BEGIN IMMEDIATE
  │                       │                       │              UPDATE WHERE v=5 ✗
  │                       │                       │              ROLLBACK
  │                       │                       │◄── conflict(current=6) ──
  │                       │                       │
  │                       │                       │ 展示冲突解决 UI
  │                       │                       │─ save(v=6, merged) ──►
  │                       │                       │              UPDATE WHERE v=6 ✓ (v→7)
  │                       │                       │              COMMIT

  │ dispatch(updated)     │                       │
```

## 7.8 事件系统的并发安全

### 7.8.1 去重 HashSet 保护

```rust
static RECENT_EVENTS: Lazy<Mutex<HashSet<(String, u64)>>> =
    Lazy::new(|| Mutex::new(HashSet::new()));

// 线程安全：Mutex 保护
// 内存安全：300ms 自动清理，不会无限增长
// 锁竞争：纳秒级，不影响性能
```

### 7.8.2 事件有序性

Tauri Event 在 Rust 侧通过 `AppHandle::emit` 发射，底层保证 FIFO 顺序。前端通过 `listen` 接收，同一事件源保证顺序。

```rust
// 保证：事件 1 先于事件 2 到达所有窗口
self.event_emitter.emit_entity_updated("article", &article_v1);  // 事件 1
// ...（其他线程不能在此插入 emit）
self.event_emitter.emit_entity_updated("article", &article_v2);  // 事件 2
```

## 7.9 Python Agent 的并发限制

| 资源           | 并发限制             | 原因                      |
| -------------- | -------------------- | ------------------------- |
| Skill 执行     | 串行，1 个活跃任务   | LLM 推理无法并行，避免 Token 浪费 |
| Bridge 回调    | 并发（只读 SQLite）  | WAL 模式支持并发读         |
| Memory 写入    | 串行（SQLite 文件锁） | 写操作天然串行            |
| Health check   | 并发（独立线程）     | 不与其他操作冲突           |

```python
# skills/engine.py
import asyncio

class SkillEngine:
    def __init__(self):
        self._current_task: Optional[asyncio.Task] = None
        self._lock = asyncio.Lock()

    async def execute(self, request: SkillExecuteRequest):
        # 取消当前任务
        if self._current_task and not self._current_task.done():
            self._current_task.cancel()

        # 串行执行
        async with self._lock:
            self._current_task = asyncio.current_task()
            async for chunk in self._run_skill(request):
                yield chunk
```

## 7.10 一致性保证总结

| 层级         | 机制              | 保证                                   |
| ------------ | ----------------- | -------------------------------------- |
| SQLite       | WAL + 事务        | ACID，写串行化，读快照隔离             |
| Rust UseCase | 乐观锁（version） | 无丢失更新                             |
| Rust Event   | Mutex + 去重       | 不重复、不过量                         |
| 前端 RTK     | Redux 纯函数       | 状态可预测、可回溯                     |
| 整体         | Event + Version   | 最终一致性 + 冲突可检测可解决          |

## 7.11 故障恢复

| 故障场景               | 恢复机制                                 |
| ---------------------- | ---------------------------------------- |
| 事务中崩溃             | WAL 自动恢复，未提交事务回滚              |
| 乐观锁冲突             | 前端冲突 UI → 用户手动合并或覆盖           |
| 事件丢失（极罕见）     | 窗口聚焦时 version-based 全量同步         |
| 连接池耗尽             | `busy_timeout` 5s + 错误返回              |
| Python Agent 崩溃      | 看门狗自动重启（最多 3 次）               |
